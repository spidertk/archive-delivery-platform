# 50 包 repair 分段性能报告

## 交付与验证

- 作业：`deliveryId=12`，继续消费批次 9，不重新创建批次或全量准备 OSS。
- 50/50 任务 `DELIVERED`，共 1,460 个原始文件，原始包 3,707,554,736 字节，最终交付 3,717,515,962 字节。
- 独立外部复核：`REAL E2E PASSED deliveryId=12 tasks=50 sources=1460`。
- 连同前两次交付，FTP 当前共 450 个 `batch_*.tar.gz`，`.partial=0`。
- 50 包首次执行因磁盘写满在 merge 阻断，清理历史已交付工作副本后按原 taskId/fence 重试成功，没有重复提交。

## repair 分段结果

50 个成功 repair 的 `output_locator.timings`：

| 阶段 | 平均秒数 | 占 repair 总耗时 | 结论 |
| --- | ---: | ---: | --- |
| copyWorkspace | 0.275 | 2.1% | 目录复制不是主要瓶颈 |
| repairRequests | 0.287 | 2.2% | 协议修复本身较快 |
| gzipPack | 8.981 | 69.7% | 第一优化目标 |
| verifyArtifact | 2.895 | 22.5% | 第二优化目标，需保留最终包校验 |
| sha256 | 0.338 | 2.6% | 可流式合并 IO，但收益有限 |
| cleanup | 0.057 | 0.4% | 不是瓶颈 |
| total | 12.881 | 100% | 不含少量进程启动等时间 |

repair 节点数据库平均耗时为 13.079 秒，包含 Python 启动等额外时间。repair total P95 为 20.434 秒，gzip P95 为 14.322 秒，verify P95 为 5.890 秒。

任务创建到全部完成共 807.411 秒，其中包含磁盘故障与人工恢复时间；首次重试到最后完成约 386 秒。这两种口径均保留，不能把完整 807 秒作为正常交付基线，也不能忽略故障恢复成本。

## gzip 1/3/5 真实包对照

在 50 包交付及外部复核结束后，使用同一台机器、三个真实 merge 工作目录分别执行完整 repair，不并发执行其他交付或下载。每个级别均完成最终包协议校验和 SHA。

| gzip 级别 | 三包合计字节数 | 平均 gzip 秒数 | 平均 repair 总秒数 |
| ---: | ---: | ---: | ---: |
| 1 | 246,583,346 | 5.518 | 10.814 |
| 3 | 241,470,674 | 6.190 | 10.325 |
| 5（当前） | 233,446,324 | 7.906 | 11.862 |

相对当前 5 级：

- 1 级：gzip 快约 30.2%，repair 总耗时快约 8.8%，产物增大约 5.6%。
- 3 级：gzip 快约 21.7%，repair 总耗时快约 13.0%，产物增大约 3.4%。
- 3 级比 1 级总耗时再快约 4.5%，产物再小约 2.1%。

**建议下一批候选值为 gzip 3 级**，但当前生产 Pipeline 仍保持 5 级。三个包的离线对照不等于 50 包并发交付验收，正式调整必须发布新 PipelineVersion，再用真实 50 包验证总吞吐、最终大小、超限率和外部 SHA。

逐包结果保存在 `gzip-benchmark.jsonl` 和各 `gzip-task-*-level-*.log`。每个包都有三种级别的 size/SHA 和分段计时。

## 磁盘问题与已实施修复

前两批成功任务的 FTP 节点均记录 `workCopyCleaned=false`，遗留约 149 GB 工作副本和 30 GB FTP 回验副本，最终导致 50 包任务磁盘写满。清理仅限已交付的 delivery 10/11 和测试临时文件，没有删除源 OSS、最终 OSS/FTP 或业务事实。

根因是 Compose 各 Worker 的 `environment` 覆盖公共 environment，清理变量未传入。现已在四个 Worker 显式配置 `ARCHIVE_CLEANUP_WORK_AFTER_VERIFY=true` 并重建，容器内读取值为 `true`。部署约束已同步到 `deploy/AGENTS.md`。后续交付仍须检查成功 FTP 节点的 `workCopyCleaned=true`，不能仅凭环境变量认定清理执行成功。

## 下一步优化顺序

1. 用新 PipelineVersion 的 gzip 3 级执行下一次真实 50 包对照，确认并发条件下的收益。
2. 保留最终包独立校验，优化 `verify_output` 的读取方式；不能为了省 2.895 秒直接跳过协议校验。
3. 可在封包写入时同步计算 SHA，减少约 0.338 秒读取，但不是主要瓶颈。
4. 达到 800 GB/10 小时仍主要依靠增加独立执行槽和实测 CPU、磁盘、网络扩展能力，单纯降低 gzip 级别不足以弥补差距。
