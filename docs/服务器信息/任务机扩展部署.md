# 任务机与交付实体扩展部署手册

本手册用于在已有主机之外增加一台交付任务机，并把一个新的 `vendorCode/entityCode` 映射到独立 `workerGroup`。主机继续作为 PostgreSQL、archive-server、PowerJob Server 和既有 Worker 的事实中心；扩展机只运行自己的 Worker，可按实际网络拓扑运行自己的 FTP 服务。

手册适用于当前 V25 批次交付基线及 V29 来源监控基线。每次扩展都必须使用新的业务键或明确核对已有业务键，不能恢复旧的追加交付流程，也不能复制一套平行 `archive-delivery` DAG。

## 1. 部署边界

扩展前先确认以下关系：

| 组件 | 主机 | 扩展机 |
| --- | --- | --- |
| PostgreSQL、archive-server、PowerJob Server | 运行 | 不部署 |
| `archive-batch` / `archive-delivery` PipelineVersion | 统一在主库发布 | 不在本机发布 |
| Worker | 既有 `workerGroup` | 新的独立 `workerGroup` |
| 工作目录 | 主机自己的 Docker `archive_data` | 扩展机自己的 Docker `archive_data` |
| FTP | 既有实体自己的 FTP | 复用指定 FTP，或在扩展机运行专属 FTP |
| SFTP | 保持既有配置 | 如机器已有 SFTP，保持原账户、密码和端口 |

必须满足：

1. 一个 `workerGroup` 只对应一台机器的本地 `archive_data`，不同机器不共享工作卷、缓存目录或 staging 目录。
2. `workerGroup`、实体和 FTP 定位必须一一对应。`group1` 与 `group2` 使用不同 FTP 时，不能把其中一个实体的 host、rootPath、账户或密码复制给另一个实体。
3. PowerJob 只负责触发和心跳；批次、任务、租约和状态都写入主库 PostgreSQL。
4. 扩展机不启动 PostgreSQL、MySQL、PowerJob Server 或 archive-server。
5. Secret 只写入受控 `.env`、systemd EnvironmentFile 或 Pipeline 节点配置，不写入 Git、Markdown、日志、证据和普通 API。

## 2. 填写部署变量

在受控终端填写变量。密码、私钥和数据库连接 Secret 不要写入本手册、命令历史或工单正文。

```text
PRIMARY_HOST=replace-primary-public-ip
WORKER_HOST=replace-worker-public-ip
WORKER_SSH_USER=root

VENDOR_CODE=replace-vendor
ENTITY_CODE=replace-entity
WORKER_GROUP=replace-new-worker-group
TASK_CONCURRENCY=3
MAX_PACKAGES_PER_ROUND=100
WORKER_COUNT=3

# FTP_MODE=existing：扩展机连接另一台已有 FTP
# FTP_MODE=local：扩展机本身就是该实体的 FTP 主机
FTP_MODE=existing
FTP_HOST=replace-ftp-host
FTP_PORT=21
FTP_ROOT_PATH=/
FTP_DATA_DIR=/srv/maas-sftp/maasData/archive/replace-entity
FTP_ACCOUNT=replace-existing-account
FTP_PASSWORD=replace-existing-password
```

`TASK_CONCURRENCY` 是整个 Worker 组的总并发；`MAX_PACKAGES_PER_ROUND` 是 `archive-batch` 每轮规划容量。两者不能互相替代，扩容时应根据 CPU、内存、磁盘和 FTP 吞吐分别设定。

## 3. 扩展部署全局锁

同一个主库只能同时进行一次实体、Pipeline 和 Worker 扩展。开始前在一个单独终端打开主库 PostgreSQL 会话并保持连接，直到登记、发布和只读验收完成：

```sql
SELECT pg_try_advisory_lock(hashtext('archive-delivery:expansion'));
```

只有返回 `t` 才能继续；返回 `f` 时说明另一名运维人员正在扩展，停止本次操作并等待。锁会绑定当前 PostgreSQL 会话，不能用一次性 `psql -c` 后立即退出，否则锁也会立即释放。完成后在同一会话执行：

```sql
SELECT pg_advisory_unlock(hashtext('archive-delivery:expansion'));
```

这个锁只协调部署配置，不能替代任务租约、Worker 认领锁或 retention 锁；不能为了取得部署锁终止运行中的任务、删除租约或直接改任务状态。

## 4. 主库扩展前检查

在持有全局锁后，先做只读检查：

```bash
ssh root@"$PRIMARY_HOST" 'docker compose -f /opt/archive-delivery-platform/deploy/docker-compose.production.yml ps'
ssh root@"$PRIMARY_HOST" 'docker ps --format "{{.Names}}\t{{.Status}}" | grep -E "archive-server|postgres|powerjob|worker"'
```

确认：

- PostgreSQL、archive-server、PowerJob Server 和既有 Worker 健康；
- 主库没有需要人工处理的 `RUNNING`/`BLOCKED` 扩展冲突；
- 新 `VENDOR_CODE/ENTITY_CODE` 不与现有业务键冲突；如业务键已存在，只核对其 `workerGroup` 和 FTP 定位，不用 SQL 覆盖；
- `WORKER_GROUP` 没有被另一台机器使用；
- 主库磁盘、数据库连接数和 PowerJob 容量足够；
- 主库 5432 只允许 `WORKER_HOST/32` 访问，PowerJob 的 7700、10010 不向公网开放。

## 5. 网络、隧道和端口

建议只开放以下方向：

| 来源 | 目标 | 用途 |
| --- | --- | --- |
| 扩展机 `/32` | 主库 `5432/tcp` | Worker 访问 PostgreSQL |
| 主库 `/32` | 扩展机 `27777` 至 `27779/tcp` | PowerJob 调度 Worker |
| 扩展机 | 指定 FTP `21/tcp` 及必要被动端口 | 交付文件传输 |
| 扩展机到主库 SSH | 仅转发主库回环 `7700`、`10010` | PowerJob 发现和心跳 |

不要把 7700、10010、PostgreSQL 或 FTP 管理面板开放到 `0.0.0.0/0`。若 `FTP_MODE=local` 且只有本机 Worker 使用 FTP，FTP 优先绑定 `127.0.0.1:21`；必须被其他内网节点访问时，再按白名单放行。

在主库创建专用 `archive-tunnel` 账户和专用密钥。`authorized_keys` 只允许转发到：

```text
127.0.0.1:7700
127.0.0.1:10010
```

同时禁止 Shell、TTY、X11、agent forwarding 和其他转发。扩展机保存私钥：

```text
/var/lib/archive-tunnel/.ssh/primary_ed25519  # mode 600
```

创建 `/etc/systemd/system/archive-powerjob-tunnel.service`：

```ini
[Unit]
Description=Archive Delivery PowerJob tunnel
After=network-online.target
Wants=network-online.target

[Service]
User=archive-tunnel
ExecStart=/usr/bin/ssh -NT \
  -o BatchMode=yes -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -o StrictHostKeyChecking=accept-new \
  -i /var/lib/archive-tunnel/.ssh/primary_ed25519 \
  -L 127.0.0.1:7700:127.0.0.1:7700 \
  -L 127.0.0.1:10010:127.0.0.1:10010 \
  archive-tunnel@replace-primary-public-ip
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now archive-powerjob-tunnel
sed -i '/[[:space:]]powerjob-server[[:space:]]*$/d' /etc/hosts
printf '127.0.0.1 powerjob-server\n' >> /etc/hosts
curl -fsSI --connect-timeout 3 --max-time 5 http://127.0.0.1:7700
nc -vz -w 3 127.0.0.1 10010
```

7700 只用于 PowerJob 发现，10010 用于心跳和调度，不能互换。隧道未建立时不要启动 Worker。

## 6. FTP 与 SFTP 选择

### 6.1 复用已有 FTP（默认）

`FTP_MODE=existing` 时：

- 不在扩展机安装或重建 FTP；
- 从该实体对应 FTP 服务器核对 `FTP_HOST`、端口、根目录、账户和权限；
- 主库实体 endpoint 与扩展机实际连接参数必须完全一致；
- 不读取、复制或修改其他实体的 FTP 账户密码；
- 上传仍使用 `.partial`、大小/SHA 校验和原子改名，禁止同名不同 SHA 覆盖。

### 6.2 扩展机同时作为该实体 FTP 主机

只有当扩展机本身就是该实体的 FTP 主机时才使用此模式。创建受控文件 `/etc/archive-delivery/ftp.env`（权限 `600`）：

```dotenv
FTP_USER_NAME=replace-existing-account
FTP_USER_PASS=replace-existing-password
FTP_USER_HOME=/srv/maas-sftp/maasData/archive/replace-entity
FTP_ALLOW_DATE_CLEANUP=false
```

账户和密码沿用机器现状，不运行改密脚本；`FTP_ALLOW_DATE_CLEANUP=true` 只能和 Pipeline 的 `cleanupOtherDeliveryDates`、专属根目录及 retention 锁一起启用。使用仓库中的 `deploy/ftp_server.py`，创建 `archive-ftp.service` 后检查：

```bash
systemctl enable --now archive-ftp
ss -lntp | grep ':21'
```

如果机器已有 SFTP，不要重置 SFTP 账户、密码或配置。当前常见 SFTP 配置是：

```text
端口：2222
ChrootDirectory：/srv/maas-sftp
ForceCommand：internal-sftp -R -d /
```

因此 FTP 写入 `/srv/maas-sftp/maasData/archive/replace-entity/file` 后，SFTP 会以 `/maasData/archive/replace-entity/file` 看到同一个文件，但 SFTP 只能读，不能改名或删除。Worker 容器的 `/data` 是独立 Docker `archive_data` 卷；写入 `/data` 的中间文件不会出现在 SFTP 中。

用一个临时 `.partial` 文件做协议验证，再删除临时文件：

```text
FTP 上传到 FTP_USER_HOME/.protocol-check.partial
FTP 原子改名为 .protocol-check
SFTP 以只读账户列出 /maasData/archive/replace-entity/.protocol-check
核对后从 FTP 删除临时文件
```

验证不得清理历史业务目录，不得覆盖已有文件。

## 7. 同步代码和创建 Worker

扩展机使用与主库相同的已测试代码，排除 Git、受控环境、构建产物和前端依赖：

```bash
export LOCAL_REPO=/path/to/archive-delivery-platform
rsync -az --delete \
  --exclude '.git/' \
  --exclude 'deploy/.env' \
  --exclude '**/target/' \
  --exclude 'web/node_modules/' \
  --exclude 'web/dist/' \
  "$LOCAL_REPO/" "root@$WORKER_HOST:/opt/archive-delivery-platform/"
```

`--delete` 只能用于扩展机代码目录，不能用于 FTP 根目录、`archive_data`、OSS 或任何业务目录。

在扩展机 `/opt/archive-delivery-platform/deploy/.env` 写入受控配置：

```dotenv
ARCHIVE_DB_URL=jdbc:postgresql://replace-primary-public-ip:5432/archive_delivery
ARCHIVE_DB_USER=archive
ARCHIVE_DB_PASSWORD=replace-production-database-password
ARCHIVE_WORKER_GROUP=replace-new-worker-group
ARCHIVE_MAX_RUNNING_TASKS=3
ARCHIVE_WORKER_DB_POOL_SIZE=4
ARCHIVE_WORKER_JAVA_OPTIONS="-Xms128m -Xmx512m"
ARCHIVE_PREPARATION_DOWNLOAD_THREADS=16
ARCHIVE_TASK_LEASE_SECONDS=900
ARCHIVE_CLEANUP_WORK_AFTER_VERIFY=true
POWERJOB_ENABLED=true
POWERJOB_APP_NAME=archive-delivery
POWERJOB_SERVER_ADDRESS=powerjob-server:7700
POWERJOB_EXTERNAL_ADDRESS=replace-worker-public-ip
```

小规格机器应减少 Worker 数量、总并发和堆上限；不要把主机 8 核 16G 的资源值直接复制到小机器。每台扩展机的 Worker 共享本机 `archive_data`，但不同机器之间不能共享。

```bash
cd /opt/archive-delivery-platform
chmod 600 deploy/.env
docker compose -f deploy/docker-compose.worker.yml --env-file deploy/.env config --quiet
docker compose -f deploy/docker-compose.worker.yml --env-file deploy/.env up -d --build
docker compose -f deploy/docker-compose.worker.yml --env-file deploy/.env ps
docker compose -f deploy/docker-compose.worker.yml --env-file deploy/.env logs --since 5m worker-4
```

核对每个 Worker：

```bash
docker compose -f deploy/docker-compose.worker.yml --env-file deploy/.env exec worker-4 printenv ARCHIVE_WORKER_GROUP
docker compose -f deploy/docker-compose.worker.yml --env-file deploy/.env exec worker-5 printenv ARCHIVE_WORKER_GROUP
docker compose -f deploy/docker-compose.worker.yml --env-file deploy/.env exec worker-6 printenv ARCHIVE_WORKER_GROUP
```

输出必须全部等于新的 `WORKER_GROUP`。日志必须显示数据库连接和 PowerJob 注册成功，不能有 Flyway、租约或连接池错误。

## 8. 主库登记实体和发布批次映射

在主库受控 `.env` 中追加一个实体槽位，保留已有实体的全部值：

```dotenv
PROD_ENTITY_COUNT=replace-count-after-add
PROD_ENTITY_2_VENDOR_CODE=replace-vendor
PROD_ENTITY_2_ENTITY_CODE=replace-entity
PROD_ENTITY_2_NAME="生产交付实体 replace-entity"
PROD_ENTITY_2_ACCOUNT=replace-ftp-account
PROD_ENTITY_2_HOST=replace-ftp-host
ENTITY_2_WORKER_GROUP=replace-new-worker-group
PROD_FTP_ENTITY_2_PORT=21
PROD_FTP_ENTITY_2_ROOT_PATH=/
PROD_FTP_ENTITY_2_PASSWORD=replace-ftp-password
```

如果 `FTP_MODE=local`，`PROD_ENTITY_2_HOST` 填扩展机的 FTP 地址；如果复用其他 FTP，则填实际 FTP 地址。账户和密码必须与 FTP 服务端现状一致。

只在 `deploy/pipelines/archive-batch-*.md` 的 `assignment.entityWorkers` 中增加新实体映射：

```json
{
  "vendorCode": "replace-vendor",
  "entityCode": "replace-entity",
  "workers": [
    {"workerGroup": "replace-new-worker-group", "maxPackagesPerRound": 100}
  ]
}
```

`archive-delivery` 由提交时的 `targets[vendorCode,entityCode,targetCount]` 选择实体，不为每台扩展机复制一份平行 DAG；只有 DAG 本身发生 review 变更时才发布新的 `archive-delivery` PipelineVersion。

在主库项目目录执行：

```bash
cd /opt/archive-delivery-platform
./scripts/local-pipeline.sh
python3 scripts/pipeline_registry.py validate
python3 scripts/pipeline_registry.py materialize archive-batch-<case>
./scripts/configure-production-pipeline.sh
```

注册脚本负责实体唯一性、PipelineVersion 和 Secret 边界。禁止用 SQL `INSERT/UPDATE` 绕过实体注册校验，禁止重发布历史交付单绑定的版本。

## 9. 分阶段验收

扩展部署本身只做预检，不自动创建批次或真实交付。真实写入必须使用唯一批次名并获得单独生产授权。

### 9.1 只读预检

1. 主库 API 返回新实体的 `vendorCode/entityCode/workerGroup` 和正确 FTP endpoint。
2. 最新 `archive-batch` PipelineVersion 的 `assignment.entityWorkers` 包含新实体和容量。
3. 扩展机所有 Worker 为 `Up`，PowerJob 隧道的 7700 返回成功、10010 可连接。
4. Worker 从扩展机访问主库 5432 成功，主库安全组没有向公网放开。
5. FTP 登录、临时文件上传/原子改名/删除成功；若有 SFTP，能看到同一物理目录中的临时文件且保持只读。
6. 主机和扩展机的 `archive_data`、FTP 根目录和 SFTP 根目录没有跨机挂载或软链接越界。

### 9.2 生产黄金验证

只有获得生产授权后，才可以执行唯一 `deliveryBatch` 的创建、独立交付提交和外部复核。证据必须记录实际 `batchDeliveryId`、`deliveryId`、`taskId`、PipelineVersion、迁移版本、OSS URI、size/SHA、源包/批次包/任务数量，以及 `SOURCE_GET`、`TARGET_GET`、`FTP_GET`、`SIZE_SHA`、`NO_PARTIAL` 复核命令。

以下情况都不算生产交付通过：容器 `Up`、PowerJob 绿色实例、Worker 心跳、API `ACCEPTED`、fake/local Node、skipped 外部检查或仅 Repository 写入。

## 10. 日常维护、升级和回退

- 升级前停止新提交，等待该 `workerGroup` 的 `RUNNING` 节点自然完成；不要删除租约或修改历史任务的 `worker_group`。
- 升级只替换扩展机 Worker 镜像和配置；保留 PostgreSQL、PipelineVersion、OSS、FTP 和 `archive_data` 历史。
- 隧道断开时先停扩展机 Worker，恢复隧道后再启动；不要开放 PowerJob 端口或改连本地 PowerJob Server。
- FTP 失败时先只读检查 host、端口、rootPath、账户权限和磁盘；不要切换到其他实体 FTP，不要重建账户或清理历史日期。
- 禁止 `docker compose down -v`、删除 `archive_data`、清空 FTP/OSS、覆盖同名不同 SHA 文件或直接把任务写成 `SUCCEEDED/DELIVERED`。
- 扩展失败时释放 PostgreSQL 全局扩展锁，保留日志和事实表，修复后重新执行预检；不要留下半登记的重复业务键。

## 11. 常见故障判断

| 现象 | 优先检查 | 处理边界 |
| --- | --- | --- |
| Worker 启动但 PowerJob 不在线 | 隧道、7700/10010、Worker 外部地址和主库白名单 | 不开放公网管理端口 |
| Worker 连不上数据库 | 主库 5432 安全组、数据库用户权限、扩展机出口 | 不复制本地数据库 |
| 任务落到旧组 | 实体 `workerGroup`、不可变 PipelineVersion、Worker 环境 | 不直接改任务表 |
| FTP 可登录但上传失败 | FTP 根目录权限、磁盘、`.partial` 和原子改名 | 不改变其他实体账户 |
| FTP 文件 SFTP 看不到 | 是否写入同一物理 FTP 根目录；是否误写 Worker `/data` | `/data` 与 FTP 根目录不是同一个卷 |
| 两人同时扩展 | PostgreSQL `archive-delivery:expansion` advisory lock | 未取得锁立即停止 |

部署完成后，把实际实体、Worker 数量、PipelineVersion、FTP 模式和只读预检结果写入受控运维记录；不要把密码、私钥或完整 `.env` 放入文档和证据。
